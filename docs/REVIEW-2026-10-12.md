# Review, 2026-10-12: utility, simplicity, and what a lab or small business needs

An outside reading of the whole repository as of commit `a750ff5` (remote
shell and screen pusher): every script under `bin/`, the WinPE task sequence
and each step, the first-logon chain, the roles, the documents and the spike
evidence. Written the day before the first physical machine (a Dell Latitude
E5570) arrives. Nothing here was run; it is a code and design review, and it
is kept in `docs/` so the findings can be ticked off or argued with in
`TODO.md` and `DEFERRED.md`.

While it was being written, commit `9317ef4` (the collector: `bin/netboot`,
`bin/enroll`, per-machine boot overrides in `http/boot/`, `docs/COLLECTOR.md`,
`docs/LAYERS.md`, `docs/MANUAL_TESTING.md`) landed on `main`. Finding 1 and
feature 1 below were re-read against it; the rest of the review predates it
and was not re-checked.

## Verdict

This is an unusually well-reasoned piece of infrastructure that is still a
lab, not a product. The design is right and the evidence discipline is better
than most commercial tooling. What stands between it and a university lab is
not more design. It is a handful of operational gaps that only show up when a
fleet of real machines meets it, and the repo has not yet met one.

## What is genuinely good, and why it matters

**The core idea is correct and rare.** Apply-image with DISM instead of
running Setup, a pristine `boot.wim` with everything injected by wimboot at
boot, and plain text as the entire control plane. Changing an install is
editing a file and rebooting the target. Nothing else in the open-source
space does Microsoft Deployment Toolkit style *builds* from a Linux box with
zero Windows infrastructure. FOG and Clonezilla clone disks; this builds
machines.

**The safety model is the right shape.** Only a machine file can set `MODE`,
a model file cannot, and `15-preflight` checks every file on the server
before diskpart runs. An unlisted machine gets a shell and is left alone.
These rules are enforced in code (`ts/env.cmd`) and re-checked by `bin/lint`,
not just documented.

**Lint with a self-test is the standout engineering decision.** Every run
breaks a scratch copy in 35 known ways and requires each defect to be
reported. A green lint actually means something. It also reads the program
list out of `boot.wim` to catch a step calling a program WinPE lacks, which
was learned the hard way (`findstr`).

**The observability is complete for its scope.** Beacons with `start` and
`ok`/`fail` per step, logs pushed every 20 s during long steps, the server
clock as the only clock, and now a remote shell and screen pusher over the
same HTTP channel. For screenless physical machines this is more than MDT
gives you.

**Evidence over assertion.** The `spikes/` directory with dated experiments,
negative controls, and verified / read / unknown tags on every claim is a
habit worth keeping whatever else changes.

## Where it falls short today

Ordered by how badly each one bites the first real lab.

1. **The re-image loop has half an answer.** `bin/vm-boot` says it itself: a
   network-first VM redeploys itself forever after `90-reboot`. On hardware,
   hands-off re-imaging needs PXE first in firmware, so every reboot would
   wipe. Disk-first firmware means a human presses F12 for every re-image,
   which contradicts the north star ("nobody at the keyboard"). Commit
   `9317ef4` supplied the mechanism: `boot.ipxe` now chains
   `boot/<uuid>.ipxe` and `boot/default.ipxe` before deciding, `bin/netboot`
   writes them, and the collector's `pdt-pxe-next` sets BootNext from Linux
   so a disk-first machine re-enters the network once. What is still missing
   is the other direction: an override that hands a PXE-first machine to its
   local disk (the choices are `collector` and `winpe`, there is no `local`),
   and anything that flips a machine there after `deployed`. A disk-first
   installed Windows also has no agent to set BootNext, so re-imaging it
   still needs RDP or a hand at F12. This is the single most important
   missing piece for a lab that re-images every term. (Now the top item of
   `TODO.md`, much smaller than it was this morning.)

2. **Disk selection is hardcoded.** `ts/diskpart/uefi-gpt.txt` says `select
   disk 0` and then `clean`. A laptop with an M.2 and a 2.5-inch SATA, or any
   machine with a USB stick inserted, may wipe the wrong disk. Preflight
   checks the server, never the target's disks; there is no size or bus
   sanity check before the wipe. (Second item of `TODO.md`.)

3. **Every machine gets a random hostname.** `http/unattend/default.xml`
   ships `<ComputerName>*</ComputerName>`, time zone UTC and en-US, all
   copied verbatim by `60-unattend`. No `NAME=` key exists. A lab needs
   LAB-A-01 through LAB-A-30; a business needs names that match its
   inventory.

4. **The shipped admin account has a blank password.** The README says so
   plainly, but it is the default path. Between first boot and the role's
   `users.ps1` re-password, the machine sits on the LAN with a
   blank-password local administrator, and only a role with a `USERS` list
   ever fixes it.

5. **The upload endpoint trusts the whole LAN.** `PUT /uploads/` in
   `bin/serve` accepts any size from any address and overwrites by path.
   Anyone on the network can fill the server's disk or replace another
   machine's `users.txt`, which holds generated passwords. Everything is
   plain HTTP, including `plain:` passwords in role files. Fine on a lab
   VLAN, not on a flat office network, and no document says which one you
   need.

6. **No BitLocker, and no TPM in the lab.** Windows 11 on real hardware will
   have a TPM. Laptops in any business need encryption with key escrow, and
   today it cannot even be tested because the lab VM has no swtpm (the
   retired v1 had one).

7. **Nothing has run on hardware.** Secure Boot certificate enrolment,
   proxy-DHCP next to a real router, Intel RST storage, and WinPE's inbox
   driver coverage are all unverified. The repo is honest about this; the
   Latitude is the right next step.

Smaller but concrete:

- No `LICENSE` file. `PLAN.md` §3.1 says pick MIT. Until then nobody can
  legally reuse this.
- No CI. Lint's self-test and a syntax pass need no Windows ISO and would run
  in under a minute on every push.
- Lint's CRLF check (`CRLF_GLOBS`, `bin/lint`) covers `ts/` and `post/` but
  not `roles/*/*.cmd` or any `.ps1`, although `.gitattributes` does. A role
  post script saved with LF passes lint and misbehaves.
- Images are not versioned. Everything says `IMAGE=base.wim`; a monthly
  re-stage overwrites the only copy and there is no rollback.
- Monthly updates are a hand chore: `pack-updates` needs you to find the
  files in a UUP set yourself. `fetch-updates` is in `DEFERRED.md`.
- `bin/status` re-parses the whole of `beacons.log` and `access.log` every
  2 s in `--watch`. Fine at ten machines, slow at two hundred, and the log
  never rotates.

**On simplicity specifically.** The code is simple; the documentation is not.
`README.md`, `PLAN.md`, five docs and a dozen spike READMEs total several
times the code, the same status paragraph dated 2026-10-02 appears in three
places, and the verification tables in the README belong in `spikes/`. A
newcomer cannot tell what to read first. Phase 6's `INSTALL.md` is the real
fix, and the README should shrink to what a stranger needs in the first hour.

Batch is the right language for WinPE and it has reached its ceiling. The
`:one` routine in `deploy.cmd`, the nested fetch loops in `60-unattend` and
the exit-code reasoning in `35-updates` are correct, but only lint keeps them
that way, and lint's own cmd parser (`commands()`) is forty lines of
heuristics. The small Python dispatcher parked in `DEFERRED.md` becomes
cheaper than more batch the moment the server has to *react* to a beacon
(release a machine on `deployed`, gate concurrent deploys), which item 1
leads to. The collector commit's `bin/netboot` keeps boot decisions as
static one-line files, which is the right call for as long as a person
writes them.

## What a university lab or small business needs added

**Before the first real machine:**

1. **Local-boot handoff**, on top of `bin/netboot`. A third `pdt_boot`
   value, `local`: one `iseq ${pdt_boot} local && exit ||` line in
   `boot.ipxe` makes iPXE return to the firmware, which boots the next entry,
   Windows after `bcdboot`. `bin/netboot <m> local` after a deploy and
   `bin/netboot <m> winpe` to re-image, with `lint` accepting the third
   one-liner. A small watcher that tails beacons and runs `netboot local` on
   `deployed` closes the loop with no human.
2. **Disk selection and a wipe guard.** A step before `20-disk` that lists
   disks, picks by bus and size or by a `DISK=` key, refuses removable media,
   and writes the chosen number into the diskpart script.
3. **Templated unattend.** `NAME=`, `TIMEZONE=`, `LOCALE=` and a generated
   `deploy` password substituted by `60-unattend`, the password uploaded to
   the write-only endpoint and never present in a served file.
4. **A swtpm in the lab VM**, so BitLocker and the Windows 11 hardware path
   are tested before they meet a laptop.

**Before anyone else runs it:**

5. `LICENSE`, `INSTALL.md`, `bin/preflight`, systemd units, and a GitHub
   Actions job running lint's self-test. All already planned as Phase 6.
6. Upload hardening in `bin/serve`: a sane body limit for logs, a separate
   location for `capture.wim`, an `allow` list for the lab subnet; one
   paragraph in `INSTALL.md` on putting deployment on its own VLAN.
7. Versioned images with a `latest` convention, and a `bin/fetch-updates`
   that pulls the current cumulative update from a UUP set, so the monthly
   chore is one command.

**Lab and small-business features, in order of value:**

8. **A read-only status page.** `bin/status --html` rendered into
   `http/status.html` and served by the nginx that already runs. Not a web
   app. It lets a student worker or office manager see the fleet without a
   terminal.
9. **Inventory.** A per-machine JSON compacted from the logs: last seen,
   image and build, role, hostname, Secure Boot state. This is what an IT
   office actually asks for, and it fixes the `status` performance problem at
   the same time.
10. **BitLocker as a role key**, with recovery keys escrowed through the
    uploads endpoint.
11. **Domain join**, starting with offline join blobs (`djoin`) served per
    machine, with the planned Samba AD lab service to verify it. Businesses on
    Entra ID will also want a documented hybrid or Autopilot hand-off, even if
    the answer is "not this tool's job".
12. **Activation guidance.** OEM keys in firmware activate automatically when
    the edition matches; otherwise a `KEY=` role or site setting and a KMS
    note. Today the word does not appear outside a `fetch-iso` comment.
13. **RDP as a role key**, which `docs/REMOTE_VISIBILITY.md` already sketches,
    so an admin can reach a deployed machine from Linux.
14. **Concurrency reality.** Thirty machines pulling a 3.5 GB image from one
    nginx is 100 GB over one NIC. Document staggered booting and a 10 GbE
    server port, or gate boots N at a time with the same watcher that handles
    the local-boot handoff.

**What not to add.** Multicast, a database, a web framework, PowerShell in
WinPE, or SMB shares. Each would undo the property that makes this repo worth
having: an administrator can read the entire control plane with `cat`.

## Recommended order

Get the Latitude deployed (`TODO.md`, Phase 5), but put the local-boot
handoff and the disk guard in first: both are cheaper to build on a VM than to
discover on a laptop with a damaged screen.
